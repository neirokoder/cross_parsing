# Кросс-парсинг PDF правил РС: методика эталона и сверки

## Цель

Довести кросс-парсинг PDF-документов (Docling HTML → JSON с добором из PyMuPDF) до
полного совпадения с эталоном: Precision = Recall = F1 = coverage = 1.0,
`type_mismatch = 0`, `structure_mismatch = 0`.

## Инструменты и команды

| Что | Команда |
|---|---|
| Документ в HTML Docling | `python cli.py docling-html --pdf <pdf>` |
| Кросс-парсинг | `python cli.py parse --pdf <pdf>` |
| Сверка с эталоном | `python cli.py compare --pdf <pdf> --etalon <etalon.json>` |
| Результат и отчёты | `data/output/<name>.json`, `report_<name>.json`, `report_<name>.md` |
| Постраничный дамп (PDF-текст, HTML, блоки парсера) | `work/etalon_build/dump_page.py` (выгрузка в `work/etalon_build/`) |
| Разметка эталона (упрощённый JSON) | `work/etalon_build/markup/<name>.json` |
| Конвертер разметка ⇄ канонический JSON | `work/etalon_build/convert.py to_markup|to_etalon <src> <dst>` |

## 1. Создание эталона

Эталон — ручная семантическая разметка документа в формате opendataloader
(`content.document.block[]`): для каждого блока задаются `type` (heading/paragraph/
list/table/image/formula), `page number`, `content`, `bounding box`; для заголовка —
уровень `level`, для таблицы — `rows[].cells[].block[]` и отдельно `columns`
(заголовок таблицы хранится ТОЛЬКО в `columns`, в `rows` — только данные), для
списка — `items[]`, для изображения — `image_key`, для формулы — `content`/`latex`.

Порядок работы:

1. Постранично выгружаются три источника (`dump_page.py`): сырой текст PDF, HTML
   Docling и текущие блоки парсера — чтобы при разметке видеть все слои рядом.
2. Страница за страницей задаются блоки в упрощённом JSON
   (`work/etalon_build/markup/<name>.json`): плоский список, короткие ключи
   (`t` — тип, `p` — страница, `c` — контент, `b` — bbox, `lvl` — уровень
   заголовка, таблица — `cols` + `rows` строками, список — `items[]`, формула —
   `latex`, image — `key`). **Решение о типе блока и уровне принимает агент,
   сверяясь с PDF** (уровни заголовков и семантика титула из HTML Docling не
   выводятся). Новый документ = новый файл разметки, без кода.
3. Особенности титульного листа:
   - «РОССИЙСКИЙ МОРСКОЙ РЕГИСТР СУДОХОДСТВА» — логотип-принадлежность издателя,
     **не заголовок** → `paragraph`;
   - уровни заголовков определяются по кеглю шрифта PDF: 48 → level 1,
     24 → level 2, 20/16 → level 3;
   - город/дата («Санкт-Петербург») — предложный регистр → `paragraph`.
4. Генерация канонического JSON (формат opendataloader):
   `python work/etalon_build/convert.py to_etalon markup/<name>.json control_sample/<name>.json`.
   Канонический вид: `content.document.block[]`, таблица — `rows[].cells[].block[]`
   и `columns` (заголовок ТОЛЬКО в `columns`, в `rows` — данные), список —
   `items[].content` + `content`, формула — `latex`.
5. Разметку из существующего эталона можно получить обратной конвертацией
   (`to_markup`) — она воспроизводит файл 1:1 (круглая конвертация проверена).

## 2. Сверка (`cli.py compare`)

Матчинг и метрики реализованы в `app/etalon/compare.py`:

- **Жадный матч по странице**: для каждого блока эталона ищется лучший блок
  результата на той же странице по сходству текста (SequenceMatcher, порог
  `DEFAULT_SIM_THRESHOLD = 0.6`; точные совпадения приоритетны).
- **Матч только между блоками одного типа** — иначе «совпадение из разных
  участков JSON». Текстовый близнец блока другого типа засчитывается как
  `type_mismatch`, а не как совпадение.
- **Image без текста** — сопоставляется по `image_key`.
- **Метрики**: P / R / F1 по блокам; `text_coverage` — доля символов эталона,
  покрытая текстом matched-пар (SequenceMatcher, не наивный `zip`);
  `structure_mismatch` — расхождение формы JSON у совпавших пар:
  таблица — `columns`/`rows`, список — `items[]`, heading — `level`,
  image — `image_key`, формула — `content`/`image_key`.
- **Отчёт** (`data/output/report_*.json|md`): summary, by_type, by_page, списки
  `missed` / `extra` / `type_mismatches` / `structure_mismatches` — точечно
  указывают, что чинить.

## 3. Цикл доводки (как достигнут 1.0)

Сверку выполняет **ИИ-агент**: он прогоняет `compare`, разбирает отчёты и для
каждого `missed`/`extra`/`structure_mismatch` просматривает постраничный дамп
(`dump_page.py`) и PDF-страницу, устанавливает причину расхождения и чинит
соответствующий слой пайплайна (см. ниже), затем повторяет цикл, пока отчёт не
будет чистым. Это обеспечивает качественный анализ, а не подгонку: каждый дефект
получает объяснение в терминах исходных данных (HTML Docling / PDF).

Правила цикла:

- После любого изменения пайплайна обязателен прогон `compare` на **обоих**
  калибровочных документах: рабочем и регресс-ориентире. Изменение принимается
  только если ориентир не просел.
- Численные оценки и списки расхождений в гид не заносятся — они быстро
  устаревают и всегда актуальны в свежих `report_*.json|md`; в гид остаются
  только описание процессов и обобщаемые принципы.

Слои пайплайна, которые может править агент (снизу вверх):

1. **Постобработка Docling HTML** (`app/algorithm/html_to_json.py`):
   нормализация ключей (таблицы включают `columns`), разрезы/склейки строк,
   подписи «Таблица N.N.N» отдельным параграфом.
2. **Добор из PDF** (`app/algorithm/pdf_extract.py`):
   `enrich_blocks_from_pdf` (добор пропущенного, bbox, формулы),
   `fix_title_page_headings` (уровни титула по кеглю, логотип → paragraph).
3. **Финальные чистки** (`app/algorithm/cross_parser.py` `_final_cleanup`):
   заголовок-одиночка в предложном регистре → paragraph; колонтитулы; пустые
   формулы; склейка разорванных абзацев (строчная первая буква фрагмента + конец
   prev не `[.!?…:;]`; маркерный фрагмент склеивается с маркером в начале,
   ссылочный фрагмент «8.1.4 и 8.1.5.» — без маркера).

**Правило**: текстовые/структурные дефекты чинятся в пайплайне. Эталон правится
только как исключение, когда расходится его собственная структура или семантика
(например, заголовки таблиц перенесены `rows[0]` → `columns`, логотип — в
`paragraph`). После любой правки эталона источник разметки
(`markup/<name>.json`) должен оставаться с ним в синхроне: перегенерация
обязана воспроизводить текущий файл.

## 4. Ключевые находки парсинга правил РС (феноменология)

Раздел для будущих алгоритмов: что известно о стилистике документов РС, дефектах
Docling и правилах, уже проверенных на практике (калибровка — 2-020101-174-5,
58 стр., F1 0.920 → 0.926; материал — 5-я, 12-я части).

### 4.1 Стилистика нормативного документа (обобщаемые признаки)

| Признак | Значение для парсера |
|---|---|
| Нумерация пунктов `1.3`, `1.3.2`, `8.1.4` (минимум 2 уровня), подпунктов `.1`, `.1.2` | Границы блоков: `_MARK_RE`, `_SUBMARK_RE` в `html_to_json.py` |
| Заголовки — ВЕРХНИЙ РЕГИСТР; уровни по кеглю PDF (48/24/20-16); предложный регистр-одиночка («Санкт-Петербург») — не заголовок | `fix_title_page_headings`, `_trim_heading_suffix` |
| Канонические обороты: «…должен быть получен с помощью формулы», «…определяется по следующей формуле», «…следующим образом:», «принимается равным/не более», «в соответствии с N.N.N» | Детерминируют границы формул и блоков (используются частично; перспектива — полноценные вербальные маркеры) |
| Пояснения к формулам: «формула, где a — …, ЕД.; b — …, ЕД.;» | Правило R1 `_split_formula_where`: разрез по «, где», левая часть с «=» — формула. Единицы измерения (`м;`, `град;`, `кг/м3;`) — маркеры конца строки определения (перспектива — сплит списка определений) |
| Условия-обнуления «X = 0, если …» | `_split_zero_if`: отдельный параграф |
| Подписи «Таблица N.N.N» (заголовок таблицы ТОЛЬКО в `columns`), «Рис. N.N.N-N» | Таблицы — уже обрабатываются; подписи «Рис.» у image-блоков ТЕРЯЮТСЯ (p51) — перспектива: caption Docling |

### 4.2 Дефекты Docling (наблюдаемые феноменологии)

1. **Склейка параграфов** — несколько пунктов в одном `<p>`: «…изолированы. 8.1.2
   Изоляционные…» → `_split_merged_paragraphs` (режет по маркерам).
2. **Разрыв предложения по строкам**: «…на плотность всей» + «системы холодильного
   агента…» — склейка в `_final_cleanup` 4.4 (строчная первая буква фрагмента +
   конец prev НЕ `[.!?…:;]`). **Осторожно**: это правило НЕ должно склеивать
   «где …» после формулы (guard: prev заканчивается `),\d)`-подобно и next начинается
   с «где »).
3. **Дробление списков**: один семантический список (пункты с подпунктами)
   Docling режет на несколько `<ul>` (после `.1…`) — `_split_lists`; и наоборот,
   последовательность пунктов «4.1.2…4.1.6» в один list — НЕ сливать обратно
   (эталон не консистентен: p22-раздельные списки vs p29-склеенные «2.7.1…» —
   склейка давала чистый минус).
4. **Многострочные формулы**: разрыв на фрагменты с выносом степеней «³»/«²» на
   отдельные строки («−1/3𝑏11𝐽𝑘» + «3 + 1/2(…)” + …) — текущий `_merge_fragments`
   склеивает только смежные. ПЕРЕСТАНОВКА фрагментов (порядок HTML ≠ вертикальный
   порядок PDF: «…накатных» + формула + «пассажирских судах;») — **не решено**;
   перспектива: восстановление порядка по `bounding box` (y, x).
5. **Формула + пояснение одним блоком** («(формула), где sпромеж.і — …») — R1
   (см. 5.1) + флаг `_where_formula`, чтобы формула не демоутилась.
6. **Типаж «формула vs параграф»** (матчер compare.py ТИПО-ЧУВСТВИТЕЛЕН —
   «совпадение из разных типов» ≠ совпадение!). Кандидат-формула: математический
   Unicode (греческий, `\U0001D400-\U0001D7FF`), «=». Демоут в параграф, если:
   начинается с кириллицы, ИЛИ ≥4 кириллических слов, ИЛИ содержит «если».
   Эталон консистентен: «s 𝑖 = min (…или…)», «s промеж.𝑖 = [(…)(…)]^1/4» — формулы
   (несмотря на «или»/«Протяженность»); «TGZmax = 0,20 м … судах;», «K = 1, если
   θe ≤ θmin», «GZmax — максимальное…» — параграфы. Исключение-артефакт эталона:
   «Mкрен = max(Mпасс, Mветер, Mспассредства).» — эталон хочет параграф.
7. **«Formula not decoded»** → подмена текстом из PDF по bbox (`pdf_extract.replace_not_decoded_formulas`).
8. **Разрядка «Т а б л и ц а 2.2.1»**, PUA-символы, дубли, колонтитулы, пустые формулы — финальные чистки.

### 4.3 Принципы, выведенные из правок

- Правила **только обобщаемые**: запрещено закладываться на номера страниц и
  единичные случаи (эталон может содержать артефакты разметки — например, p47
  разбивает «где» и «A = 0,5(Al+Ad)» на два блока, а p24 держит «где P = 120 Н/м2»
  одним — оба требования не удовлетворить одним правилом; такие места помечаются
  и пропускаются).
- Каждый дефект объясняется в терминах исходных данных (HTML Docling / PDF / bbox),
  а не посредством подгонки под эталон; направление правки — слой пайплайна.
- Разряды цены правила измеряются прогоном `compare` (matched/extra/missed по
  страницам в `report_*.json`) — грубые правила, дающие минус, откатываются сразу
  (`_merge_adjacent_lists` был отклонён так).
- Многие «missed» — это НЕ пропуски, а «раздельно в эталоне, слитно в результате»
  или тип-мисматч после демоута — всегда сверять с полным текстом блока,
  а не с первыми 80 символами отчёта.

### 4.4 Текущее состояние

Актуальные показатели (F1, P/R, coverage, списки `missed`/`extra`) — только в
свежих `data/output/report_*.json|md`, в гид не дублируются. Остатки расхождений
относятся к обобщаемым классам: склейка/разрез абзацев и списков, тип-мисматчи
«формула vs параграф», фрагменты формул и пояснений — каждый класс чинится
правилом пайплайна либо помечается как артефакт эталона (см. 4.3).

### 4.5 Регресс-ориентир (ВАЖНО)

Вторая калиброванная часть используется как регресс-ориентир: её эталон
пересобран, прогон `compare` должен держать единицу. Обязательный прогон после
любой правки пайплайна (см. правила цикла, разд. 3).

## 5. Сверка других документов

- Тот же `cli.py compare --pdf <pdf> --etalon <эталон>`, эталон того же формата.
- Эвристики калибровались на 2-020101-174-12 (паттерн «регистр судоходства»,
  «Приточные и вытяжные каналы», пороги кеглей титула, порог сходства 0.6) — на
  новом PDF они могут требовать расширения или рекалибровки; точки вмешательства
  видны в `missed` / `extra` / `structure_mismatches`.
